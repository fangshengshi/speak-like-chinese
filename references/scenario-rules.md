# 场景适配规则

中文 AI 味检测和改写需要根据目标场景调整强度与风格。本文件供 SKILL.md 引用。

> **场景识别失败的代价很大**——把学术论文当小红书润色会让原文失去严谨性；把合同当公众号润色会改变法律义务。识别没把握时，主动询问用户场景，不要默认。

---

## 场景识别启发式（用单关键字识别会误判，必须用反向特征确认）

LLM 在不确定场景时按以下顺序判断：

1. **用户明确指定场景** → 直接采用
2. **用关键字初判 + 反向特征确认**（任一关键字命中后必须再扫反向特征）

| 初判线索 | 初判场景 | 反向确认（命中即否决） |
|---|---|---|
| 含「参考文献」「引用」「[1]」「et al.」 | 学术 | 全文第一人称段落 > 30%、感叹号密度 > 千分之三、含网络流行语 |
| 含「家人们」「姐妹们」「上链接」「绝绝子」 | 小红书 | 含「参考文献」、含「方法论」、含「致：/ 兹有」、含 `<table>` `<sup>` 等正式排版 |
| 含「谢邀」「先上结论」「以上」 | 知乎 | 同时含「家人们」「姐妹们」（说明只是模仿语气，不是真知乎） |
| 含「致：」「兹有」「特此通知」「应/不得/承担/赔偿」 | 公文/法律 | 含网络流行语、含表情符号 |
| 含 `## ` 标题 + 多级列表 + 代码块 | 技术文档 | 含「我之前试过」「我遇到过」（个人随笔混入） |
| 含「兹证明」「乙方应」「合同期内」「违约金」 | 法律文书 | — |
| 含「病历」「诊断」「处方」「剂量」「用法」「禁忌」「不良反应」 | 医疗文书 | 含网络流行语、营销转化话术 |
| 含「项目里程碑」「关键路径」「OKR」「PoC」「演示文档」 | 商业 PR / 白皮书 | 含网络流行语 |
| 含「教学目标」「考试要点」「知识点」「【例题】」 | 教育课件 | — |

3. **关键字 + 反向特征双向冲突时主动询问用户**：例如初判为小红书（含「姐妹们」）但又含「参考文献」——可能是学术论文里反思 AI 时引用了网络语，也可能是营销稿假装学术。这种情况下不要默认走任何场景，问一下用户。
4. **都不匹配时** → 默认按「公众号·中等强度」处理，但**禁用** `formal_to_colloquial` 和 `definite_to_soft` 表（避免误改正式文本的语义）。

---

## 1. 学术论文（去模板化）

**目标**：保持学术严谨，去除「具有重要意义/综上所述」等八股。**不**追求口语化。

**保留**：专业术语、被动句（中文学术中合理）、完整句式、正式连接词（适度）。

**重写**：
- `具有重要意义` → 改为具体贡献：「本研究在 <具体维度> 上提出了 <具体发现>」（具体维度若原文已说明则照写，未说明则保留 [TODO: 补具体贡献]）
- `综上所述` → 直接陈述结论
- `研究表明` → 「<研究方> 在 <年份> 的研究显示」（必须可追溯；若原文未提供，保留 [TODO: 补研究方/年份]）
- `值得注意的是` → 删除

**禁止**：
- 第一人称口语化（「我觉得」「我之前」）
- 表情词（「挺」「蛮」「有点」）
- 网络词
- 把「对某市居民进行调查」编造为「问了 500 个居民」（具体数字幻觉，参见 SKILL.md 改写示例反例）

---

## 2. 公众号

**目标**：观点明确、有故事、有节奏。不过度黑话也不过度口语。

**保留**：适度专业、第一人称、具体场景（前提：原文有）、长短句变化。

**重写**：
- 删除互联网黑话（high severity）
- 开头改为具体场景或问题切入
- 三段式列举改为自然叙述或两点列举
- 结尾留有余地，避免「具有重要意义」

**节奏**：段落 3-5 句。单句段落（如「对吧？」）每 500 字最多 1 个。

---

## 3. 知乎回答

**目标**：理性、有人味、有结构感。

**允许**：
- 「先上结论」「以上」等知乎特色（视情况）
- 数据引用（**必须有真实出处**，原文未提供 → 保留 [TODO]）
- 适度专业术语
- 第一人称

**重写**：
- 删除黑话（high/mid severity）
- 数据引用必须真实——AI 改写时禁止编造数字、研究、出处
- 三段式 → 两点 / 四点 / 自然叙述

---

## 4. 小红书

**目标**：极度口语化、情感丰富、个人经历为主。

**允许**：
- 大量第一人称
- 表情符号（适度，标题以外）
- 「姐妹们」「家人们」等称呼
- 短段落（每段 1-2 句）
- 「啊啊啊」「绝了」「真的真的」等情绪化表达

**禁止**：
- 学术八股
- 长论述（>5 句段落）
- 客观中立语调
- **凭空编造个人经历**（如原文没提到「我之前试过」就不要写「我之前试过」）

**注意**：仍要去除 AI 装饰性 emoji（标题前的 🚀💡✅）。

---

## 5. 微博

**目标**：极简、碎片、情绪。

**允许**：
- 单句即可
- 话题标签
- 不完整句法
- 网络流行语

**禁止**：
- 任何 AI 模板（全部 high severity 黑话/八股）
- 长论述

---

## 6. 文艺 / 小说 / 散文

**目标**：画面感、情感细腻、语言有质感。

**允许**：
- 长句、复杂句、修辞
- 具体细节描写（前提：原文有素材，绝不凭空编造）
- 情感表达
- **三段式排比**——鲁迅、汪曾祺等大量使用排比三段，文学语境中是合法修辞，不一刀切禁用
- **否定排比**（如「不是 X 而是 Y」）单段单处合法递进保留；同段 ≥2 处才视为模板

**禁止**：
- 互联网黑话（破坏文学语感）
- 模板化 -着翻译腔（「象征着 X 的 Y」「反映了 X 的 Y」——这是 AI 翻译腔不是文学排比）
- 凭空捏造时间地点人物数字

---

## 7. 商务 / 公文 / 政府报告

**目标**：保留正式度，**只**去模板化和谄媚。

**保留**：被动句、专业术语、正式连接词、完整句式、确定性表达。

**重写**：
- 谄媚（「希望这对您有帮助」「好问题」）→ 删除
- 协作交流痕迹（「如果您想让我扩展」）→ 删除
- 装饰 emoji 标题 → 删除
- 弯引号 → 中文引号或直角引号

**禁止**：
- 口语化（「我觉得」「搞 / 弄」）
- 第一人称（除非个人陈述类公文）
- 表情词
- **绝对化软化**——公文需要确定性，「必然/绝对/毫无疑问」在公文里是合法表达，不软化为「大概率」（这是与其他场景的关键区别）

---

## 8. 法律文书 / 合同（与公文规则差异）

**目标**：保留法律严谨性，仅去 AI 谄媚和装饰。

**保留**：所有义务词（应/不得/承担/赔偿/兹证明/特此声明）、所有绝对化术语（必然/确定/明确）、所有正式连接词、所有被动句。

**重写**：仅删除谄媚痕迹和装饰 emoji。

**禁止**：
- 任何 `formal_to_colloquial` 表的替换（「实施 → 做」会改变法律义务级别）
- 任何 `definite_to_soft` 表的替换（「必然 → 大概率」会失去法律确定性）
- 任何第一人称注入
- 任何模糊化处理

---

## 9. 医疗文书 / 医嘱 / 病历

**目标**：保留医学严谨性和责任边界，仅清理谄媚、装饰 emoji 和明显宣传腔。

**保留**：诊断名、药品名、剂量、频次、禁忌、不良反应、检查指标、医嘱格式、被动句和规范表达。

**重写**：仅删除「希望这对您有帮助」「当然！」这类聊天痕迹，以及标题前装饰 emoji。

**禁止**：
- 把「每日 2 次」改成模糊表达
- 把「禁忌」软化成「不太建议」
- 注入个人经历或口语化安慰
- 凭空补充病因、疗效、预后、剂量或替代药物

---

## 10. 商业 PR / 白皮书

**目标**：正式但要传播力，介于学术和公众号之间。

**保留**：行业术语、专业数据（要有真实出处）、企业第一人称（「我们」）。

**重写**：
- 删除互联网黑话（赋能/抓手/闭环——PR 里这些是负担不是加分）
- 删除「在当今社会」开场白
- 删除「具有重要意义」结尾，改为具体业务影响（前提：原文已说明）

**禁止**：
- 个人第一人称（「我觉得」）→ 改为企业「我们认为」或客观陈述
- 网络流行语
- 编造数据（PR 数据出错的法律和品牌后果都很重）

---

## 11. 教育课件 / 科普

**目标**：严谨但易懂，介于学术和公众号之间。

**保留**：核心专业概念、必要术语（首次出现时给中文加英文括注）、举例。

**重写**：
- 学术八股（具有重要意义）→ 改为「这一部分的关键是……」
- 长抽象句 → 短句加比喻
- 删除空泛连接词

**允许**：
- 第一人称引导语（「我们来看一下」「想想看」）
- 反问句（「为什么会这样呢？」）
- 适度具体例子（前提：例子真实可查或为典型教科书例子）

**禁止**：
- 凭空编造研究/案例
- 把术语口语化到失真（「光合作用」不能改成「植物喝阳光」）

---

## 12. 技术工件 / changelog / 工作周报 / commit message（豁免维度 D）

**目标**：完全保留，不要套用维度 D 的「编号回引/工时估算模板/无主语并列」规则。

**识别**：含以下信号即按本场景处理：
- `## v` 或 `## 版本` 开头 + 列表（release notes / changelog）
- `### 本周完成` / `### 本周计划` / 工时数字 + 任务列表（工作周报）
- `修复` / `新增` / `优化` / `重构` 开头 + 引用 issue/PR 编号（commit message / PR description）
- 含 `closed #123` / `fixes GH-456` / `Co-Authored-By` 等 git 协作标记
- 含函数签名、参数表、return 字段（API doc / docstring）
- 含 `期望` / `实际` / `重现步骤`（bug report）

**保留原样**：
- 编号回引（`#123` / `[CR-456]`）保留——这是工程协作必要标识
- 表格化压缩列表保留——这是行业规范
- 工时估算（`~2h` / `预计 3 天`）保留
- 短句无主语（`修复登录失败` / `新增导出按钮`）保留——commit message 标准格式

**仍要去除**：
- 装饰 emoji 标题（🚀 v1.2.0）→ 改为「v1.2.0」
- 谄媚（「希望对您有帮助」）
- AI 生成的「至关重要 / 深入探讨 / 织锦 / 格局」等翻译腔——技术工件也不该有这些

**禁止**：
- 把 commit message 改写成自然句（「修复登录失败」改成「我们解决了用户在登录页面遇到的问题」是负优化）
- 把 changelog 列表展开成段落（破坏可读性和可解析性）
- 把工时估算改写成「这件事大概要花两个小时」（同行评审/PM 看了不知道工时数据）

---

## 跨场景通用红线

不论什么场景，以下三条不变：

1. **不编造原文没有的细节**（数字、来源、人名、时间、地点、个人经历）
2. **专业术语在专业语境里保留**（参见 blacklist.json 的 `context_safe_when` 字段）
3. **场景识别没把握时主动询问**，不要凭单一关键字默认
